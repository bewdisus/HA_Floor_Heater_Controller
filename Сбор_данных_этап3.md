# Сбор данных — этап 3

**Проект:** автономный контроллер тёплого пола, Wemos D1 mini / ESPHome  
**Цель:** накопить данные о тепловой инерции конкретного пола, чтобы на этапе 4
подобрать `tau` и `delta_max` адаптивной компенсации по реальным графикам, а не
по предположениям (ТЗ §7.4, §14).

**Статус:** методика согласована 2026-11-19. Срок сбора — 2–4 недели, минимум
10 полных циклов нагрева и остывания.

## 1. Что собираем

Телеметрия публикуется самим контроллером, отдельного оборудования не нужно.

| Сущность | Зачем |
|---|---|
| `sensor.esp_smart_heater_floor_temperature` | основная кривая температуры пола |
| `sensor.esp_smart_heater_lower_threshold` | нижний порог гистерезиса в каждый момент |
| `sensor.esp_smart_heater_upper_threshold` | верхний порог гистерезиса в каждый момент |
| `binary_sensor.esp_smart_heater_pump_running` | фактическое состояние насоса |
| `sensor.esp_smart_heater_ntc_resistance` | контроль измерительного тракта |
| `text_sensor.esp_smart_heater_controller_state` | состояние автомата (`HEATING`, `IDLE`, …) |
| `text_sensor.esp_smart_heater_last_reason` | причина последнего переключения |
| `sensor.esp_smart_heater_uptime` | признак перезагрузки контроллера |
| `sensor.esp_smart_heater_wi_fi_signal` | качество связи во время сбора |

Температура, сопротивление и напряжение помечены `state_class: measurement`,
поэтому в HA для них ведутся долговременные статистики (5-минутные агрегаты),
которые не удаляются вместе с историей.

## 2. Сколько и в каких условиях собирать

- **Длительность:** 2–4 недели, но не меньше **10 полных циклов** «нагрев →
  выключение → остывание → включение».
- **Разные условия:** желательно поймать циклы утром и вечером, при разной
  температуре за окном — от этого зависит скорость остывания.
- **Разные уставки:** 2–3 цикла на целевой 25 °C и 2–3 на 27 °C (если
  используются). При смене уставки фиксировать дату и время — иначе графики
  несравнимы.
- **Не менять гистерезис** во время сбора: он должен быть одинаковым, иначе
  перелёт нельзя сравнивать между циклами.
- Режим — `Auto`. `Manual ON` и `Off` в статистику не идут.

## 3. Что смотреть на графиках

Для каждого цикла нужны три увеличения:

1. **Момент отключения.** `T_max − Upper Threshold` = перелёт после выключения
   насоса, и время от выключения до пика. Это главная величина для `delta`:
   чем больше перелёт, тем раньше надо выключать.
2. **Первые 10–20 минут после включения.** Наклон `°C/мин` — скорость, которую
   будет считать алгоритм этапа 4. Нужно понять её типичный и максимальный
   диапазон: при `tau` компенсация `v · tau` не должна упираться в предел.
3. **Остывание.** Наклон после выключения: он определяет, насколько быстро
   пол возвращается к нижнему порогу, и какой простой насоса считать нормальным.

## 4. Что из этого следует для этапа 4

- `v` — типичная и максимальная скорость нагрева, °C/мин;
- перелёт — ориентир для `delta_max` (в ТЗ предварительно 0.5 °C, это надо
  проверить);
- `tau` — подбирается так, чтобы `T_off_adaptive = T_target + H/2 − v·tau`
  срабатывал примерно за время перелёта до пика;
- длительность цикла — исходные данные для минимальных времён ON/OFF (этап 5).

## 5. Настройка Home Assistant

### 5.1. Хранение истории

По умолчанию HA пишет всё; для двух-четырёх недель сырых данных достаточно
увеличить срок хранения:

```yaml
# configuration.yaml
recorder:
  purge_keep_days: 45
```

Оценка объёма: 4 сущности с обновлением раз в 5 секунд дают порядка 2–3 млн
строк за 45 дней. Если база уже большая, срок можно сократить до 30 дней, но
тогда сбор надо закончить раньше.

`recorder.include` применять не стоит: он глобальный и отключит запись истории
для всех остальных сущностей дома.

### 5.2. График

```yaml
type: history-graph
title: Пол — температура, пороги, насос
hours_to_show: 24
entities:
  - entity: sensor.esp_smart_heater_floor_temperature
  - entity: sensor.esp_smart_heater_lower_threshold
  - entity: sensor.esp_smart_heater_upper_threshold
  - entity: binary_sensor.esp_smart_heater_pump_running
```

Для разбора одного цикла удобнее карточка `statistics-graph` по
`floor_temperature` с периодом 5 минут за нужные сутки и переключение
`hours_to_show` на 6–12 часов.

### 5.3. Счётчики насоса (в HA, без записи во flash контроллера)

Создать в UI `Settings → Devices & Services → Helpers → Counter` с именем
`pump_starts`, затем:

```yaml
automation:
  - alias: "Насос: счётчик пусков"
    triggers:
      - trigger: state
        entity_id: binary_sensor.esp_smart_heater_pump_running
        to: "on"
    actions:
      - action: counter.increment
        target:
          entity_id: counter.pump_starts

sensor:
  - platform: history_stats
    name: Насос включён всего
    entity_id: binary_sensor.esp_smart_heater_pump_running
    state: "on"
    type: time
    start: "{{ now().replace(month=1, day=1, hour=0, minute=0, second=0) }}"
    end: "{{ now() }}"
```

Счётчик пусков и наработка нужны на этапе 5 для оценки минимальных времён
ON/OFF и ресурса насоса.

## 6. Передача данных для анализа

Для подбора параметров нужны либо CSV-выгрузки за характерные циклы, либо
доступ к API HA (`history/period`) на время анализа. Токен создаётся в
`Профиль → Токены длительного доступа` и **не коммитится в репозиторий**.
Формат, который достаточно прислать: `timestamp, floor_temperature,
lower_threshold, upper_threshold, pump_running` с шагом 5–60 секунд за
2–3 характерных цикла.

## 7. Критерий завершения этапа 3

- в HA появились `Lower Threshold`, `Upper Threshold`, `Uptime`, `Wi-Fi Signal`;
- у температуры, сопротивления и напряжения есть статистики (проверяется в
  `Developer Tools → Statistics`);
- накоплено не менее 10 полных циклов за 2–4 недели;
- помеха измерения проверена по протоколу из [Анализа_данных_18-19.11.2026.md](Анализ_данных_18-19.11.2026.md) (аппаратная проверка с отключённой нагрузкой);
- по графикам определены `v`, перелёт и скорость остывания;
- данные и выводы зафиксированы в [Документация_реализации.md](Документация_реализации.md)
  и `CHANGELOG.md`.

## 8. Предварительный анализ (18–19.11.2026)

Первые 35,5 часа данных разобраны в отдельном документе:
[Анализ_данных_18-19.11.2026.md](Анализ_данных_18-19.11.2026.md). Кратко:

- алгоритм работает корректно: пуск на 29.47 °C, останов на 30.54 °C при порогах 29.5 / 30.5;
- цикл 64 мин, 22 пуска в сутки, скважность 32 %; нагрев 0.047 °C/мин, остывание 0.025 °C/мин;
- измерение шумит сильнее шага АЦП: σ = 0.27 °C при шаге 0.17 °C, до 431 скачка > 0.5 °C в сутки;
- 46 % переключений реле (42 из 91) — дребезг, сгруппированный в моменты пуска насоса;
- перелёт после останова не наблюдается и заведомо меньше 0.2 °C.

Поэтому длительный сбор по §2 начинается **после** аппаратной проверки из §7
анализа: иначе помеха попадёт в статистику и исказит параметры для этапа 4.

По этим же данным идентифицирована тепловая модель и построен расчёт цикла:
[Модель_тёплого_пола.md](Модель_тёплого_пола.md) — `τ` = 167 мин, `T_amb` = 26 °C,
`Q/C` = 0.075 °C/мин, `T_eq` = 38,5 °C.
